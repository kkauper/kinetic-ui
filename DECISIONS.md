# Decisions

What was chosen, what was rejected and why, and the known limits. Each entry is short on purpose: the code is the detail, this file is the reasoning.

## Architecture

### Headless core, thin bindings
**Chosen:** `@kinetic-ui/core` holds both models (motion and form) as plain TypeScript stores. `@kinetic-ui/react` is a handful of hooks of a few lines each over `useSyncExternalStore`.
**Why:** the brief is a model that any UI can consume. Keeping React out of the core makes the store contract (`getState`, `subscribe`) the product and React just one consumer. The README shows Vue and Svelte wrappers in a few lines to prove the point.
**Rejected:** a React context/provider library. It would tie the model to one framework and hide the contract behind components.

### Core compiles without DOM types
**Chosen:** `packages/core/tsconfig.json` uses `lib: ["ES2022"]` and `types: []`. Anything platform-specific (storage, `devicemotion`, the element that receives `data-motion`, timers) comes in through small structural interfaces defined in core (`KeyValueStorage`, `MotionEventTarget`, `Scheduler`, `{ setAttribute }`).
**Why:** "no React or DOM imports" is enforced by the compiler instead of by review. It also makes everything testable in Node with fakes.
**Cost:** a few structural casts of `globalThis` for default timers and the default accelerometer environment.

### One store shape for everything
Form model, motion store and the Show-full policy all implement `ReadableStore<T>` (`getState`, `subscribe`). Snapshots are immutable and **keep the same reference when nothing changed**, which `useSyncExternalStore` requires and which avoids needless re-renders in any framework. No-op actions (back at step 0, deferring an already deferred field, repeating the same validation error) do not emit; unit tests pin this.

### Components never touch sensors
Product UI (`FullForm`, `Stepper`, field renderers) only reads `useMotion(store).state`. Sources are created in `apps/demo/src/stores.ts` and only the `demo-controls/` folder (the stand-in for "input devices and tooling") switches them. Moving mode reaches CSS through `bindMotionAttribute`, which sets `<html data-motion="still|moving">`.

## Motion model

### Cadence heuristic plus hysteresis (demo-grade)
**Chosen:** acceleration magnitude, minus a slow moving average (gravity), lightly smoothed; a step is a rising crossing of an adaptive threshold with a refractory period; cadence is 1000 / median step interval over a 4 s window. Both averages use time constants (about 1 s for gravity, 55 ms for the step signal) and the refractory period is 200 ms, so results do not depend on the sample rate (phones deliver 50-100 Hz); with a fixed 0.3 coefficient and a 250 ms refractory period, a 4 steps/s shake sampled at 50 Hz was read as 2 steps/s, inside the walking band. Walking is cadence within 1.5–2.5 steps/s. A pure reducer (`stepMachine`) commits a change once the opposite condition has built up `enterMovingAfterMs` (3 s) or `exitMovingAfterMs` (10 s) of progress (a leaky accumulator, see below).
**Why:** cheap, explainable, runs on any phone browser, and the slow exit means a pause at a traffic light does not flip the UI back and forth. The asymmetric timing biases towards the full form: simplifying late is cheaper than simplifying wrongly.
**Rejected:** native activity recognition (Core Motion, Activity Recognition API). Not reachable from a web page and out of scope by brief. ML classifiers: overkill for a prototype and hard to explain.
**Adaptive threshold and regularity check:** the first version used a fixed threshold of 1.2 m/s², tuned on synthetic traces with a 3 m/s² bounce. On a real iPhone held in the hand (reading the form while walking) the bounce is only about 0.3 to 1 m/s² after smoothing, so the threshold was never crossed and cadence stayed 0 (reproduced: synthetic 1.8 steps/s at amplitude 0.5, 0.8 and 1.0 all read 0). Now the threshold is `max(stepThreshold, 0.8 × envelope)`, with the envelope the 2 s moving average of |signal|; `stepThreshold` became the floor and its default dropped to 0.3 m/s² (0.35 missed a 0.5 m/s² bounce at 2.4 steps/s with noise 0.3; 0.3 caught all hand-held traces tried and still ignores a still phone with noise up to 1 m/s²). A lower threshold lets hand jitter and noise produce steps, so cadence is only reported when the step intervals are regular (stdev / mean ≤ 0.25 after folding, see below); otherwise 0. **Calibrated on a real trace** (iPhone, iOS 18.7, hand-held, 16.6 s, 58 Hz, committed as `cadence-recorded.json`): steady 1.8 steps/s, but iOS dropped events for 470 ms once, which doubled one step interval and pushed the interval CV to 0.38–0.41, so cadence read 0 for 3 s. Missed-step folding (an interval within ±25 % of 2× or 3× the median counts as 2 or 3 intervals) fixes that: after folding the real walk's CV is 0.04–0.13 at every checkpoint and the store switches to moving at 7.5 s (with the old 5 s delay) and stays there. The CV limit is 0.25 (it was 0.3): with folding on, a synthetic random-interval jitter fixture reached 0.28 and read a false 2.4 steps/s at 0.3. Margin: real walk ≤ 0.13, synthetic walks ≤ 0.05, jitter fixtures 0.19–0.28 where they have enough steps. The margin against jitter is thin: with random bumps at 150–1550 ms intervals, about a third of the 4-step windows still have CV ≤ 0.25, so the regularity check alone is not a strong jitter filter; the cadence band and the enter delay do the rest. More recorded traces (especially other people's) should drive any further change. Known limit: random bumps can line up by chance (one of six random jitter seeds read a steady 1.2 steps/s, which is outside the band anyway). *Rejected: only lowering the fixed threshold*: one value has to sit below the weakest hand-held bounce yet above the wiggles between the steps of a strong pocket bounce, and the two ranges overlap. Ratio, envelope time constant and CV limit are module constants, not `MotionConfig` fields, to keep the FFI and the generated Swift/Kotlin unchanged; they become config fields with the next FFI change. Web-only debugging aids (estimator diagnostics, raw-sample tap, 20 s trace recorder in the debug sheet) are not mirrored in Rust.
**Enter delay 5 s → 3 s:** the owner found the switch slow (about 3 s until cadence first appears plus 5 s). The regularity check now rejects bumps and jitter, so the commit delay can shrink; the hysteresis stays asymmetric (leaving still takes 10 s). Replaying the real iPhone trace through the store, it switches to moving at 5.5 s and stays there; none of the still or jitter fixture traces switch. Both delays can be changed live in the debug sheet.
**Leaky accumulator instead of reset-on-miss:** the owner found the switch even slower after the 3 s change. Measured by replaying the real iPhone trace through the store: the trace itself is fine (cadence first in band at 2.5 s, moving at 5.6 s, one flip in 16 s), but real walks are uneven, and every single "not walking" evaluation (a dropped-sample gap, an irregular window, the stricter CV limit) reset the countdown to zero. Variants of the real trace: one extra 400 ms gap took 7.9 s to switch, two gaps 10.9 s with 6 resets, interval jitter of ±25 % 8.2 s. Now each direction has a progress counter: it grows 1 ms per ms while the input argues for the change and shrinks by `DECAY_RATIO` = 2 ms per ms while it does not (dropped at 0); the change commits when progress reaches the delay. `pending` / `pendingSince` keep their snapshot meaning (the lean, and when it started from 0); progress itself is only in the machine state and the debug diagnostics. Ratio 2: walking must be seen about two thirds of the time to get there, so a gap costs twice its length, while a real stop still cancels (a short walk of 2 s followed by 1 s of stillness is back at zero; a 4 s traffic-light pause only builds 4 s of the 10 s needed and is paid back at twice the speed). 1.5 was slightly faster on the gap variants but lets a stop linger longer; 3 was slower on the gap variants (7.4 s against 7.0 s) without a visible benefit on the stop cases. The ratio is a module constant for now, a config field with the next FFI change. Time to moving after the change (real trace, then variants): 5.6 s, +400 ms gap 5.7 s, three gaps 7.0 s, jitter ±15 % 5.5 s, ±25 % 5.8 s, jitter ±15 % plus a gap 7.3 s; the still and jitter fixtures never switch. Remaining slow case: gaps of 300 and 500 ms in the first 7 s still take 10.3 s, because there the estimator itself (not the hysteresis) loses the cadence for seconds after each gap (the odd interval fails the regularity check for the whole 4 s window); a median-based regularity measure fixed that case but let a jitter fixture through, so it was not adopted. *Rejected: a shorter delay alone*, which brings back the flicker the delay exists to absorb.
**Measured (synthetic 1.8 steps/s walk in Chromium, before the 3 s change):** still → moving after 7.1 s (cadence window warm-up plus 5 s), moving → still 11.2 s after walking stopped.
**Tuning:** every constant lives in `packages/core/src/motion/config.ts`. Use the debug sheet on a phone.

### Sources are adapters
`MotionSource` has `start(emit)` (may be async) and `stop()`. Shipped: manual toggle, simulator (seeded, deterministic, also used by tests) and accelerometer. Sources that already know the state (the manual toggle) emit `state` samples, which **bypass hysteresis**: an explicit user statement should act immediately, and running it through the cadence estimator would decay it back to still after 10 s.

### Clock rule
Samples are stamped with the store's clock (`Date.now()` by default), never with `event.timeStamp`, which has a different origin. The store, estimator and sources must share one clock; it is injectable for tests.

### Accelerometer and the iOS permission
**Chosen:** an explicit "Walking mode" button. `DeviceMotionEvent.requestPermission()` (iOS 13+, and present in newer Chrome) only succeeds during a user gesture, so the path click → `setSource` → `start` → `source.start` → `requestPermission()` has **no `await` before the permission call**. This was verified in Playwright (`navigator.userActivation.isActive` was true inside the call).
**Failure modes, each with a visible message:** insecure context (sensors need HTTPS), API missing, permission denied, no data within 3 s (desktop browsers expose the API but never fire it).
**Rejected:** starting sensors on page load. It is impossible on iOS and would be a surprising permission prompt elsewhere.

### Activity samples from native classifiers
**Chosen:** a third sample kind, `activity` (`stationary | walking | running | cycling | automotive | unknown` plus a 0..1 confidence), for the OS classifiers on iOS (Core Motion) and Android (Activity Recognition). It goes through the same hysteresis as cadence, because OS classifiers flicker too. Only `walking` with confidence >= 0.5 counts as walking by default (`movingActivities`, `minActivityConfidence`). iOS low/medium/high maps to 0.33/0.67/1; Android transitions have no confidence and report 1.
**Why running and vehicles are not walking:** same reasoning as the cadence band. The full form is the safe direction when the user is running or riding.
**Not on the web:** there is no browser source for it; it exists so the model is the same on every platform.

### Live tuning
`store.configure(partial)` replaces the immutable config and re-evaluates; the cadence estimator reads the current config through a getter. The debug sheet uses it for the cadence band (session-only, nothing persisted).

## Shared spec and conformance

**Chosen:** `packages/spec` holds language-neutral JSON: the form schema, fixtures for the reducer, the walking classifier, the cadence estimator (generated accelerometer traces with expected cadence and a tolerance), the store (fake clock, no raw sensor data), the form model and the email helpers. `core/src/conformance.test.ts` runs every case against the TypeScript implementation; the Rust core and the Swift and Kotlin packages will run the same files. Test cases double as documentation of the behavior.
**Why:** parity across languages is only real if it is tested; a prose spec drifts. The cadence traces are committed data, so implementations do not need to reproduce the TypeScript generator's PRNG.
**Cost:** fixtures are a second place to update when behavior changes on purpose. Unit tests stay for the TypeScript-specific contracts (same snapshot reference, no emit on no-ops).

### Design tokens from one source
**Chosen:** `kinetic.tokens.json` in the DTCG format, built by Style Dictionary 5 into CSS, Swift and Kotlin (committed outputs). Custom formats keep the output short and scoped (`:root` plus `[data-motion='moving']`).
**Note:** the question font size is now `18px` / `24px` instead of `1.125rem` / `1.5rem`, because tokens are unit-agnostic numbers shared with native platforms (where they become pt, dp and sp).

## Rust core and native bindings

### One Rust core for Swift and Kotlin, driven by platform time
**Chosen:** `crates/kinetic-core` (pure Rust, `serde` only) implements both models; `crates/kinetic-ffi` exposes it to Swift and Kotlin with UniFFI (proc-macro mode, bindings generated by `scripts/generate-bindings.sh` and committed under `native/generated`). The web keeps `@kinetic-ui/core`.
**Why:** the logic (cadence estimator, hysteresis, form semantics, exact error messages) is the part that must not drift between platforms; the platform glue (sensors, timers, storage, UI) is the part that must be native. A Rust core gives one implementation behind idiomatic generated Swift and Kotlin APIs.
**Time belongs to the platform:** the core has no clock, thread or timer. The app calls `push_sample` for each sensor reading and `tick(now)` on its own timer, with times in milliseconds. That keeps the core deterministic and testable with fixtures, avoids a runtime inside a mobile library, and lets each platform use its own sensor and scheduling APIs (Core Motion, `SensorManager`, `Timer`, coroutines).
**Parity:** the Rust core and the TypeScript core run the same JSON fixtures in `packages/spec` (`crates/kinetic-core/tests/conformance.rs` mirrors `conformance.test.ts`); Swift and Kotlin run them through the generated bindings later.
**Rejected:**
- *Kotlin Multiplatform:* the Swift API of a KMP library is shaped by Kotlin/Objective-C interop, and the toolchain is heavy for a model this small.
- *Rust compiled to WASM for the web:* the brief asks for plain TypeScript, and WASM adds async initialisation and a binary to ship. The TypeScript core stays; fixtures keep it honest.
- *Hand-porting to Swift and Kotlin separately:* three implementations to keep in sync, with the fixtures as the only safety net.

### Show-full policy lives in the engine
In TypeScript the policy subscribes to the store. The Rust engine has no subscriptions, so it owns the policy state and consults it after each snapshot change (release the force once the detected state is `still`). The `motion-store.json` fixtures pass unchanged. The FFI layer adds the observer list.

### Listeners run outside the lock
`MotionEngine` and `FormModel` in `kinetic-ffi` hold their state in a `Mutex` (UniFFI objects are `Send + Sync`). After a change they release it, copy the listener list, release that lock too, and only then call `on_change`. A listener can call `snapshot()` or a mutating method without deadlocking; the cost is that a listener may observe a state newer than the change that woke it. Pinned by a re-entrant listener test.

### UniFFI licence
UniFFI is MPL-2.0: file-level copyleft that applies to changes to UniFFI's own files. Using it unmodified as a dependency is compatible with this Apache-2.0 project. The generated bindings are our output, not UniFFI source.

### Apple: static XCFramework, MainActor stores, Core Motion sources
**Packaging:** `scripts/build-xcframework.sh` builds `kinetic-ffi` for five Apple targets, merges the simulator and macOS slices with `lipo`, and wraps the three static libraries in `KineticFFI.xcframework` (a plain module map, not a `framework module`). The generated `kinetic.swift` and the token file are committed so the package reads without a build; the XCFramework is git-ignored. *Rejected: cargo-swift* (one more tool to install and pin for about 30 lines of script) and *committing the binary* (large, unreviewable diffs).
**Stores:** `MotionStore` and `FormStore` are `@MainActor @Observable`. The engine's listener fires on whatever thread pushed a sample, so it hops to the main actor to refresh the published snapshot; the store's own calls refresh synchronously. Sources are `Sendable` classes that emit from private queues; a generation counter drops samples and `start()` results from superseded starts. The generated module stays in Swift 5 mode, everything we wrote is Swift 6.
**Activity mapping:** `CMMotionActivity` has independent Bools, so the source picks one class by priority (automotive > cycling > running > walking > stationary > unknown) and maps confidence low/medium/high to 0.33/0.67/1.0, matching the TypeScript doc comment; with the default threshold of 0.5 a `low` reading never counts as walking. The mapping is a pure function so it is tested without a device. `CMPedometer` cadence would be a possible future source (steps per second, no classifier) but the engine already derives cadence from acceleration, so it is not used.
**Accelerometer source kept:** it runs the same heuristic as the web demo (parity, comparable debug numbers) and is the fallback where activity data is unavailable or denied. `ActivitySource` is the default on a real iPhone: the motion coprocessor classifies walking at much lower power than 50 Hz sampling.
**Demo project:** XcodeGen (`project.yml`) generates the Xcode project. *Rejected: a committed hand-written `.xcodeproj`* (unreviewable diffs, merge conflicts).
**Demo UI parity (iOS):** the SwiftUI demo follows the web demo. *Summary:* the done step is a read-only "Review your answers" (deferred questions first, answers with "Change" pills, a large full-width "Create account" in the bottom bar, "Back" as a small pill above it); "Review full form" is gone. *Focus and keyboard:* all text-like questions use one `TextField` with stable identity (never keyed by field id) and its own `@FocusState`, set on appear and on each step change; SwiftUI buttons do not take focus, so Next keeps the keyboard open, and Return is Next. Choice, Yes/No and slider steps use `@AccessibilityFocusState` to put VoiceOver on the control, the summary on its heading. Device-only behaviour, not verifiable in CI. *Bottom-anchored layout:* a scroll view whose content is at least screen height and bottom-aligned, with the Back/Later/Next bar in a bottom `safeAreaInset` (kept above the keyboard by the system). *Pill and contrast parity:* forced dark, Radix slate/blue values, dark text on the accent (5.78:1 against white's 3.26:1), slate-9 boundaries (3.68:1) on inputs, cards, switch, slider track and soft/outline buttons, every button a capsule, 8 pt radius for inputs and cards; the switch and slider are custom drawn for the boundary (the slider keeps the system slider's accessibility through `accessibilityRepresentation`). *Font:* Hanken Grotesk (OFL-1.1) bundled in the app and registered with `UIAppFonts`, so there are no runtime downloads; `Font.custom(_:size:relativeTo:)` keeps Dynamic Type. The pinned readout is a single status pill that opens the debug sheet (`.sheet`, medium and large detents).
**Verification:** on Linux (Swift 6.4.1 via swiftly, the Rust library linked through a throwaway system-library target) the bindings, all platform-neutral `KineticUI` code and its Swift Testing suite compile and pass. Not verifiable without a Mac: the XCFramework script, the Core Motion sources, the SwiftUI environment code and the whole demo app.

### Android: generated Kotlin as a source dir, StateFlow stores, Transition API
**Packaging:** the generated `uniffi.kinetic` Kotlin and the token file `packages/spec/generated/KineticTokens.kt` (package `ui.kinetic.tokens`, fine as is) are added to the `:kinetic` library as extra source directories, so there is one source of truth and nothing is copied or hand-edited. UniFFI's Kotlin uses JNA; the library depends on the `jna` AAR (it carries the Android natives). `scripts/build-android.sh` builds `libkinetic_ffi.so` for three ABIs with cargo-ndk into a git-ignored `jniLibs` folder. AGP 9 compiles Kotlin itself, so `org.jetbrains.kotlin.android` is not applied; only the Compose compiler plugin is.
**Stores:** `MotionStore` and `FormStore` mirror the engine/model into `StateFlow`s (snapshot, show-full state, source id, running, error). The engine's listener fires on whichever thread pushed a sample, so flow updates run under one lock (a stale read can never overwrite a newer one); `source.stop()` is called outside it. A generation counter drops samples and `start()` results from superseded starts, as in TypeScript and Swift. Start failures do not throw out of `start()`: they land in `error` and the call returns `false`, so a UI coroutine cannot crash on a denied permission. Compose gets the state through `CompositionLocal`s (`LocalMotionState`, `LocalKineticMetrics`) filled by `KineticMotionProvider`, which collects with `collectAsStateWithLifecycle`.
**Activity Transition API:** it reports transitions (ENTER/EXIT of WALKING, RUNNING, ON_BICYCLE, IN_VEHICLE, STILL; ON_FOOT is not supported), not a stream, and carries no confidence. ENTER maps to the matching `ActivityKind` with confidence `1.0`; EXIT of the current activity with no ENTER in the same batch reports `Unknown` (Play services usually delivers EXIT(old) and ENTER(new) together, and ENTER wins). Latency varies by device and is seconds, not milliseconds; the engine's hysteresis sits on top of that. The mapping is a pure class (`TransitionTracker`) with unit tests, including a test that pins its constants to Play services' own.
**Delivery:** an explicit, `FLAG_MUTABLE` `PendingIntent` (Play services must add the result extras, so `FLAG_IMMUTABLE` cannot work; Android 14+ throws for a mutable PendingIntent with an implicit intent) to a receiver registered at runtime with `RECEIVER_NOT_EXPORTED`. **This combination follows the documentation but has not been confirmed on a device.** `stop()` removes the updates and unregisters the receiver. The runtime permission `ACTIVITY_RECOGNITION` is requested by the app (the library only checks it and throws a user-facing exception); the manifest also declares Play services' own permission for Android 9 and older.
**Accelerometer fallback:** `AccelerometerSource` feeds `TYPE_ACCELEROMETER` (gravity included, m/s^2) at `SENSOR_DELAY_GAME` through the engine's step detector from a private `HandlerThread`. It needs no permission and no Play services, so it is the fallback on devices without them and gives numbers comparable to the web demo.
**`:bindings-test`:** a plain Kotlin/JVM module that compiles the generated Kotlin and the library's platform-neutral code (`MotionStore`, manual and simulated sources, via an exclude list) and runs JUnit 5 against the host build of the Rust library (`uniffi.component.kinetic.libraryOverride`). It proves the FFI end to end (records, enums, typed errors, foreign `ChangeListener` and `FormStorage` callbacks, re-entrancy) without an emulator, and CI runs it. `:kinetic` and `:demo` are included in `settings.gradle.kts` only when an Android SDK is configured, so that module builds anywhere.
**Bug found by compiling the Kotlin:** the FFI error `InvalidSchema { message }` generated a Kotlin property that clashes with `Throwable.message`; the field is now `reason`.
**Verification:** `:kinetic` and `:demo` compile and `:demo:lintDebug` passes against Android SDK 37; the JVM tests pass. Not verified without a device: the Transition API delivery described above, the permission flow, the accelerometer on real hardware, TalkBack behaviour, and the Compose UI at runtime (no instrumented tests).
**Demo UI parity (Android):** the Compose demo follows the web demo. *Summary:* the done step is a read-only "Review your answers" (heading focused on entry; deferred questions first with "Answer now"; each question with its answer or a muted "Not answered" and a small "Change" pill whose accessibility label is "Change: <question>"; Next from a changed question returns to the summary); "Create account" is a large full-width pill in the bottom bar with "Back" as a small pill above it, and "Review full form" is gone. *Focus and keyboard:* every step change focuses the step's control with `FocusRequester` (text: the field plus `keyboard.show()`; choice, Yes/No, slider: the control, so TalkBack lands on it; the summary: its heading). All text-like questions are one `OutlinedTextField` at the same place in the composition (never `key(field.id)`), so focus and the keyboard survive from one text step to the next; only label and `KeyboardOptions` change in place (Email vs. text may restart the input session, focus stays). Compose buttons do not take focus on touch, so tapping Next or an email chip leaves the field focused; IME Next is Next. *Layout:* `enableEdgeToEdge()` with dark bars, `windowSoftInputMode="adjustResize"`, and `imePadding()` then `navigationBarsPadding()` on the bottom bar, so it sits right above the keyboard. The stepper is bottom anchored: a scroll area whose content is at least as tall as the viewport, a weighted spacer on top, then progress ("Question n of N", polite live region), the "N for later" chip and the status pill, the question, the field. The demo controls scroll with that content so they give way when the keyboard is up. The full form keeps top-to-bottom flow. *Pills and contrast:* one dark Material 3 scheme with the Radix slate/blue values of the web theme; dark text on the accent (#111113 on #0090ff is 5.78:1, white 3.26:1); slate-9 (3.68:1) for text fields, unselected cards, the off switch track, the inactive slider track and outlined/tonal buttons; every button is a `CircleShape` `PillButton` (small/regular/large, filled/tonal/outlined), inputs and cards keep 8 dp; a selected card has an accent border and a check icon; "Saved for later" is a 3 dp accent bar in the start margin plus a badge. *Demo controls:* pill tags (Simulate walking, Walking mode, Debug), a `ModalBottomSheet` for the readout and tools (accelerometer and simulator included), one opaque status pill in the layout, error notice cards with the web wording. *Font:* Hanken Grotesk (OFL-1.1, `packages/spec/brand/fonts`) as one variable TTF in `res/font`, one `Font` entry per weight with `FontVariation.weight`, set in every text style of the theme; no Google Fonts provider, no runtime download, text stays in sp. *Test:* a Robolectric Compose test in `:demo` (Simulate walking, focus on the email field, Next keeps the same field node focused with the new label, summary with five rows and "Create account"). Not verifiable without a device: the real soft keyboard (show/hide, `adjustResize` with different IMEs), TalkBack focus order and announcements, and the variable font on a real GPU renderer.

## False positives (being wrong is expected)

- **Debounce:** the hysteresis above.
- **Persistent "Show full form" control** in moving mode, always in the same place (the mode bar under the demo controls). A tap forces the full form until the detector really sees the user stop, so the next walk can simplify again. After 3 taps moving mode is suppressed for the session (page lifetime), with a visible "Turn back on". The policy is headless (`createShowFullPolicy`).
- **Deferred fields:** deferrable questions get "Later" in the stepper, collect under "N questions for later" (always visible as a chip, listed on the done step) and are highlighted "Saved for later" in the full form.
- **Answers survive every switch:** both presentations render the same `FormState`; every answer is saved to the model and to localStorage on change.

## Form

### One schema, two presentations
`signup.schema.json` is the source of truth; `defineSchema` validates it at load (unique ids, known kinds, `required` and `deferrable` are mutually exclusive, because a required field cannot be postponed).
**Stepper rules:**
- Entering moving mode jumps to the first unanswered, non-deferred question; Next and Later also land there, so already-answered questions are skipped. Back is plain step-back, so answers can still be reviewed.
- Auto-advance (300 ms, so the choice is seen) only after unambiguous taps: choice cards and the Yes/No toggle. Text and slider never auto-advance.
- The toggle is a Switch in the full form but two large Yes/No cards in the stepper. A switch that auto-advances is ambiguous (did the user mean to flip it back?) and is a small target.
- The slider's displayed default ("Never") is confirmed by pressing Next, because Radix only reports value changes, so the minimum could not otherwise be chosen.
- **The walking flow ends in a read-only summary, not an editable form.** After the last question the stepper shows "Review your answers": each question with its answer and a small "Change" pill that goes back to that one question (Next then returns to the summary through the jump-to-first-unanswered rule), deferred questions first under "Questions for later" with "Answer now", and one large "Create account" pill in the thumb bar. Why: the previous done step offered "Review full form", which dropped a walking user into the dense form the mode exists to avoid. "Show full form" stays as the escape hatch. Create account normalizes the email and validates everything; the first invalid question is opened with its input focused. The summary focuses its heading (there is no input) and the live region says "Review: 5 of 5 answered".
- Back is a large button in the bottom thumb bar plus a swipe-right gesture (ignored when it starts on an input or slider).
**Reduce, don't rearrange, with one documented exception:** the header, demo controls and mode bar (with "Show full form") keep their positions in both modes, and moving mode removes content rather than moving it. The exception is the stepper itself, which anchors to the thumb zone: it fills the viewport (`100dvh` minus the header and controls) with a flexible spacer on top, then progress, question, field, helper text and the Back/Later/Next bar. The input and every control sit in the lower part of the screen, reachable with one thumb, and the keyboard pushes nothing around because the input is already right above the bar. The full form keeps its normal top-to-bottom flow.
**Focus and the keyboard:** see "Accessibility basics" below. Text-like steps render one `<input>` element for all consecutive text steps.

### Persistence
`createStoragePersistence(() => window.localStorage, key)`: the storage getter itself, `getItem`, `JSON.parse` and `setItem` are all wrapped in try/catch, because Safari private mode, blocked storage and quota errors throw. Corrupt or mismatched data (different schema id or version) is ignored; the form then renders empty. `currentStep` and errors are not persisted (they are view state).

## UI and Radix Themes

### Dark theme
**Chosen:** `<Theme appearance="dark" accentColor="blue" grayColor="slate" radius="large">`, pill-shaped (`radius: full`) tags and links, `color-scheme: dark` and `<meta name="theme-color">` (#111113, Radix slate-1) so the phone's browser chrome matches. Dark only, no toggle.
**Why:** the demo is used outdoors on a phone and a dark UI with Radix tokens keeps contrast predictable; the visual language follows the owner's reference (header with logo and GitHub pill, pill tags, hero, tabs).

### Font
**Chosen:** Hanken Grotesk (OFL-1.1), self-hosted as a variable font via `@fontsource-variable/hanken-grotesk`, so the demo makes no third-party font requests (GDPR). Set through Radix's `--default-font-family` / `--heading-font-family` in `tokens.css`; code stays monospace.

### Hash-routed landing page
**Chosen:** `#/` is a landing page (what it is, install snippets, the model), `#/demo` is the sign-up demo. A 10-line `useHashRoute` hook over `hashchange`; no router dependency, and it works on any static host without rewrite rules. `?debug` lives before the hash, so `/?debug#/demo` works. On a route change focus moves to the page's `<h1>` and the document title updates.
**Rejected:** a router library (overkill for two pages) and path routing (needs host rewrites).

### Radix Themes
**Chosen:** Radix Themes for Slider, Switch, RadioCards, TextField, Button, Badge and Callout. Keyboard and ARIA behavior come from Radix primitives, so the demo concentrates on the motion-specific decisions.
**Rejected:** hand-built controls (re-implementing well-solved accessibility is a poor use of a prototype) and headless primitives alone (more styling work, and visual polish is explicitly secondary).

### Moving mode is a token set
- The `--k-*` variables (target size, gaps, question type size, thumb-zone padding, slider track and thumb) are generated from `packages/spec/tokens/kinetic.tokens.json` into `generated/tokens.css` and swapped under `[data-motion='moving']`; `apps/demo/src/tokens.css` only uses them. Targets are at least 56 px in moving mode (measured: Back/Next 56 px).
- Radix levers are mapped in one place (`ui/useUiSize.ts`): Theme `scaling` 100% → 110% and component `size` 2 → 3.
- No per-component overrides scattered across files.

### Radix overrides (deliberate, documented)
1. **Slider thumb size.** Radix's largest Slider thumb is about 14 px (`--slider-thumb-size: calc(var(--slider-track-size) + var(--space-1))`). Too small to hit while walking. Override, scoped to moving mode: `[data-motion='moving'] .rt-SliderRoot { --slider-track-size: var(--k-slider-track); --slider-thumb-size: var(--k-slider-thumb); }` (12 px and 32 px, from the tokens). The thumb's `::before` hit area is 3× the thumb, so 96 px. Uses Radix's own variables, so it survives minor upgrades, but relies on the internal class name `.rt-SliderRoot`.
2. **Slider thumb ARIA.** Radix Themes spreads `aria-*` props onto the Slider root, but the element with `role="slider"` is the thumb, which received no accessible name and no `aria-valuetext`. A small layout effect sets `aria-labelledby`, `aria-valuetext` ("Weekly", not "2"), `aria-describedby` and `aria-invalid` on the thumb. Radix never renders these attributes itself, so they are not overwritten.
3. **TextField.** No override needed: `TextField.Root` forwards `type`, `inputMode`, `autoComplete`, `autoCapitalize`, `autoCorrect`, `spellCheck` and `enterKeyHint` to the inner `<input>` (verified in the rendered DOM).

### Fixed, blurred header and a large title that collapses into it
**Chosen:** the header is `position: fixed` on every page (`--k-header-h` = 64 px + `env(safe-area-inset-top)`), background `color-mix(in srgb, var(--color-background) 72%, transparent)` with `backdrop-filter: saturate(160%) blur(16px)` (`-webkit-` prefixed too; an `@supports not` rule makes it opaque where unsupported). A 1 px hairline (`box-shadow`, so the height never changes) appears only after the page has scrolled (`data-scrolled`). Page content starts below it (top padding on `.k-app`, which is `border-box` so the page still fits 100dvh exactly: the stepper and the sticky thumb bar are unaffected, re-measured: input in the lower half, bar flush with the viewport bottom, same `<input>` across Next, 390x500 keyboard layout).
**Focus Not Obscured (WCAG 2.4.11):** `html { scroll-padding-top: calc(var(--k-header-h) + 8px) }`, so a focused element is scrolled below the header, not under it. Chromium centres focused elements, which hides a missing padding, so it was verified with `scrollIntoView({block: 'nearest'})` from below: with the padding no focusable ends under the header, without it the tabs, the demo tags and the inputs end at y = 0.
**Landing large title:** one element, the page's single `<h1>` "Kinetic UI" (logo + wordmark), lives in the header and is drawn at the old hero-h1 size (`clamp(2.25rem, 9vw, 3.25rem)`: 36 px text / 48 px logo on a phone, 52 / 69 px on desktop) over an empty, `aria-hidden` slot in the hero. One passive `scroll` listener sets `--k-collapse` (0 to 1) once per frame (`requestAnimationFrame`); CSS turns it into `translate3d` + `scale` (no layout, no font-size animation; it shrinks from the large size, so text stays crisp). The title moves with the content and docks after 64 px of scroll at the compact size (24 px logo / 18 px text, centred with the GitHub pill). Measurements (target position and scale) are taken on mount, resize, slot resize and font load, never while scrolling. No easing or delay, so `prefers-reduced-motion` needs no special case: it follows the finger.
**Structure:** on the landing the brand is the `<h1>` and not a link (it is the home page; an `<h1>` inside an `<a>`, or a link to the current page, adds nothing); on other pages it is the home link and the page has its own h1. An `<h1>` inside `<header>` is valid and axe-clean. Route changes still focus the h1 (and now also scroll to the top).
**Rejected:** CSS scroll-driven animations alone (`animation-timeline: scroll()` is not in Safari/iOS yet), and animating `font-size` (layout on every frame).

### Input tags follow device capability
**Chosen:** `ui/useMotionCapability.ts`: `canSense = isSecureContext && 'DeviceMotionEvent' in window && matchMedia('(pointer: coarse)') && matchMedia('(hover: none)')`, re-evaluated on the media queries' `change` events. On a capable device (phone, tablet) the tag row shows Walking mode and Debug; elsewhere Simulate walking and Debug. The Debug sheet has an Input section with both controls on any device.
**Why not user-agent sniffing:** it lies (iPadOS reports a Mac), and the real question is whether a sensor can deliver data. Desktop Chrome exposes `DeviceMotionEvent` but has no sensor, so feature detection alone says yes wrongly; a coarse pointer without hover is what phones and tablets report (touch laptops keep a fine pointer and hover as primary); an insecure context cannot use the sensors at all.
**Fallback:** when Walking mode fails (denied, no data, unsupported, no HTTPS) the notice's "Use Simulate walking instead" still works and also reveals the Simulate walking tag for the rest of the session, so it can be switched off again. A change of capability only changes which tag is visible, never the motion state.

### Logo
**Chosen:** an original gyroscope drawing: gimbal circle, a tilted ring (lower half in front of the axle, upper half behind it) and an axle that sticks out above and below. Single 1.5 px strokes on a 24 px grid (thinned from 2 px; the axle break is 1 unit on each side of the front ring), so it still reads at 16 px (an earlier double-ring version was a blob at that size). Android: `strokeWidth` 4.5 at the 3x scale. One master, `packages/spec/brand/logo.svg` (`currentColor`); `npm run icons` in `packages/spec` renders the favicon, touch/PWA icons and the iOS app icon (light and dark) with Playwright, and the Android adaptive icon is the same geometry as a vector drawable.
**Why:** a gyroscope reads as "motion and orientation", the phone's motion sensors. It is a metaphor only: the model uses the accelerometer and the OS activity classifier, not the gyroscope.

### Accessibility basics
- Real `<label>`s, or `aria-labelledby` for groups.
- Errors linked with `aria-describedby`, and `aria-invalid` on the control.
- Visible `:focus-visible` outlines.
- **On a step change, focus goes to the step's control** (the input; the first radio card, Yes or the selected one; the slider thumb), not to the heading. This reverses an earlier choice (heading focus, so the keyboard would not pop up unasked). Why: the one-thumb flow is "type, Next, type"; the keyboard should stay up from the email step to the name step instead of closing and reopening (layout jumping open → closed → open is also an accessibility problem), and the control's label is the question, so screen readers announce it. Progress ("Question 2 of 5") stays in an `aria-live="polite"` region. The done step has no control, so it focuses its heading.
- **Same element across text steps.** All text-like fields are one component (`TextInputField`, email is a format of it) and the stepper gives consecutive text steps the same React key (`stepper-text-input`). The `<input>` is never remounted; `id`, `name`, `type`, `inputMode`, `autoComplete`, `value` and the `<label for>` change in place, so focus and the virtual keyboard survive. Verified: same element handle, zero blur events across the email → first name transition.
- **Thumb-bar buttons do not take focus on pointer input** (`pointerdown`/`mousedown` → `preventDefault`, shared as `keepFocus`), so tapping Back, Later or Next does not blur the input. Keyboard users still Tab to them and press Enter or Space; Enter in the input is Next (`enterkeyhint="next"`).
- **iOS limit.** Safari opens the keyboard only for `focus()` called inside a user gesture. Entering moving mode from the "Simulate walking" tag renders the stepper with `flushSync` and focuses the input in the same tap handler, so the keyboard opens. A sensor-triggered switch (no gesture) and the 300 ms auto-advance after a choice still call `focus()`: Android Chrome may show the keyboard, iOS focuses the control without it until the user taps. Not testable in Chromium; needs a real iPhone.
- **Keyboard-aware layout.** The viewport meta has `interactive-widget=resizes-content`, so Chrome on Android resizes the layout viewport and the bar stays above the keyboard. iOS Safari does not resize it, so `useKeyboardInset()` publishes `--k-keyboard-inset = max(0, innerHeight - visualViewport.height - visualViewport.offsetTop)` on `<html>` (resize and scroll events; guarded when `visualViewport` is missing). The stepper pads its bottom by it and the sticky thumb bar sits at `bottom: var(--k-keyboard-inset, 0)`.
- On a failed full-form submit, focus goes to the first invalid control.
- `prefers-reduced-motion` disables transitions and animations; the mode-change view transition becomes a 150 ms opacity crossfade (see "Mode-change transition").
- **Mode-change transition (shared-element morph).** *Chosen:* the hard switch between the full form and the stepper is a same-document View Transition (`document.startViewTransition`, Chromium and Safari 18+, feature-detected). The field the user is on (the one `jumpToFirstUnanswered` lands on, computed before the transition; on the way back the stepper's current field) is the only element with `view-transition-name: k-active-field`, set on its block in the old layout and on the matching block in the new one, so it visibly moves between its place in the form and the thumb zone instead of vanishing. The rest crossfades with a small vertical slide, the thumb bar (`k-thumb-bar`) and the stepper header (`k-step-head`) slide in from the bottom. Duration and easing are tokens (`--k-motion-duration` 350 ms, `--k-motion-ease` `cubic-bezier(0.2, 0, 0, 1)` in `tokens.css`). *Reduced motion:* group animations are off and old/new fade for 150 ms, opacity only. *Fallback:* without the API, when the page is hidden, or on first load, the switch is instant exactly as before (stepper rendered with `flushSync` inside the tap handler). `Demo` keeps a `shown` mode that follows the store mode through the transition, so the old UI stays up until the browser captured it. *iOS keyboard:* the transition callback runs asynchronously, outside the gesture, so in the tap handler (layout effect of `Demo`, still inside the `flushSync`) a hidden but focusable proxy input (`ui/KeyboardProxy.tsx`, 1 px, opacity 0, 16 px font, `aria-hidden`, `tabindex=-1`, `inputMode` of the target field) takes focus when `navigator.userActivation.isActive` and the target is a text field; the stepper's own layout effect then moves focus to the real input, which keeps the keyboard open. *Back to the full form:* focus goes to the same field's control (the user's place), or the form heading when on the summary. *Announcement:* a polite live region says "Simplified for walking: one question at a time" or "Full form" immediately on a mode change, not on load. *Rejected:* a hand-rolled FLIP animation (needs measuring both layouts and fights React remounts); a slide-only transition (does not show where the input went). Chromium-verified; the proxy's keyboard behaviour on a real iPhone is not.
- **Control boundaries are at least 3:1 (WCAG 1.4.11).** Tags, GitHub/Copy/notice pills, soft and outline Radix buttons and the tab list use `--k-control-border` (slate-9: 3.68:1 on the page, 3.43:1 on gray-2 surfaces). slate-8 was rejected: 3.01:1 on the page but 2.80:1 on gray-2. The old slate-6 border was 1.65:1. Pressed tags (3.72:1) were already fine. The same colour outlines text inputs, unselected choice cards (via Radix's `--base-card-surface-box-shadow` variable), the switch track when off and the slider track (3.68:1 each; Radix hardcodes those three, so one rule each replaces the shadow). Selected cards keep the accent outline, a checked switch its accent fill. Disabled controls are exempt from 1.4.11 and keep Radix's muted text and faint fill without the outline, so Back on the first step still reads as disabled.
- **Text on solid blue buttons stays dark** (#111113 on blue-9 is 5.78:1; white would be 3.26:1 and fail 4.5:1).
- **One button shape: pill.** Every Radix Button goes through `ui/Pill.tsx` (`radius="full"`), not the Theme radius, so inputs and cards keep the Theme's large radius. Native pills (tags, links, notice action) are 9999px already. Verified by script: every button and link has a radius of at least half its height.
- **Focus rings sit outside the shape.** Pills and tab triggers use the global 2 px outline with a 2 px offset (it follows the radius); the segmented tab list does not clip it (no overflow, 6 px padding). The slider thumb has one circular outline (3 px, offset 3 px) and nothing on its `::before` hit area.
- **One left edge.** Headings, labels, inputs, cards, switch, slider and buttons share one x. The "Saved for later" cue is a 3 px bar in the gutter (`left: -12px`) plus the badge, so it never shifts content.
- Contrast comes from Radix's palette (gray-11/12 on gray-1/2 in dark); axe reports no violations on the landing and demo pages. One override: solid accent buttons use the page background as text color (`--accent-contrast`), because white on Radix's bright dark-mode blue is only 3.3:1. Focus rings use accent-10, one step lighter than Radix's default, to stay clear on dark surfaces.

## Email input
Mobile keyboard (`type="email"`, `inputmode="email"`, `autocomplete="email"`), autocorrect, auto-capitalization and spellcheck off. Domain chips (@gmail.com, @icloud.com, @outlook.com), typo suggestions by edit distance ("gmial.com, did you mean gmail.com?") and whitespace normalization are pure functions in `core/form/email.ts`. The suggestion never blocks submitting: the user may really mean that domain.

Chips use `onPointerDown` → `preventDefault` so the input keeps focus and the phone keyboard does not close and reopen. Normalization runs on blur and again before validation (Next and submit) for every `format: 'email'` field.

## Demo tooling

- **Demo controls are a row of pill tags** under the header (Simulate walking or Walking mode depending on the device, plus Debug; see "Input tags follow device capability"): horizontally scrollable, no visible scrollbar, 44 px tall; the first two are `aria-pressed` toggles whose state is shown by a ring/check icon as well as the tint (not color alone). They stand in for an input device, not product UI, so they do not grow in moving mode. The row is `role="group"`, not `role="toolbar"`: a toolbar promises arrow-key navigation we do not implement, and three buttons reachable with Tab are simpler and correct. The stepper no longer depends on how tall this area is (it is bottom-anchored), which removes the earlier problem of controls in flow pushing the stepper down.
- **Source errors are notification cards** (`Notice`: icon, title, body, optional "Use Simulate walking instead", dismiss; errors `role="alert"`, info `role="status"`, slide-in only without `prefers-reduced-motion`). The wording is mapped from core's error strings in one file (`demo-controls/notices.ts`). The notice appears when the user taps Walking mode, not on load; dismissing it returns focus to the Walking mode tag.
- **Debug is a bottom sheet** (`DebugSheet`, a Radix Themes `Dialog` restyled: focus trap, `aria-modal`, Escape, backdrop tap, focus returns to what opened it). One tap on the Debug tag shows everything, with no second button and no accordion: the live readout (all rows, including activity and the error), the "Keep readout on screen" switch, then the tools (simulated cadence slider, Use simulator, min/max cadence, reset Show-full, clear answers), all with 44 px targets. Dragging the handle or header follows the finger and closes past 80 px or on a flick; drags that start on inputs, buttons or the slider are ignored. Slide-up only without `prefers-reduced-motion`. The Debug tag is a plain button (`aria-haspopup="dialog"`, `aria-expanded`), not a toggle. *Rejected: an in-flow panel* (pushed content around) *and a native `<dialog>`/popover* (more custom focus handling for the same result).
- **The pinned readout is one opaque pill** (`● still · 1.8 steps/s · 20 s`, plus `→ moving 3.1 s` while a change is pending; the dot is filled for moving and hollow for still, and the text says it too). An earlier multi-row translucent overlay collided with form fields and wrapped the error text. The pill is in the page flow so it can never cover content and the space it needs is part of the layout: a sticky row at the end of the full form, and in the stepper a part of the header row of the bottom group (no extra height, never over the input or the thumb bar, also with the keyboard open). It is a button that opens the sheet, not a live region, and shows no error text (errors live in the Notice). It appears after Debug was opened once, or on load with `?debug`; the switch turns it off (`localStorage` `kinetic-ui:debug-readout`, default on).
- **The simulator source** makes the hysteresis testable on a desktop without a phone (1.8 steps/s → moving after about 7 s).

## Hosting
Cloudflare Workers with static assets, at `kineticui.kauper.co`, deployed by Cloudflare's Git integration (Workers Builds): every push to `main` deploys, other branches get preview URLs. Why: a custom subdomain on the owner's own domain, whose DNS zone is already on Cloudflare (so the domain and certificate are one step), a free tier that covers static assets, and Git-connected deploys with preview URLs per branch. Cloudflare's docs say to start new projects on Workers, so Pages was not used. Vite `base` is `/` because the site sits at the subdomain root. GitHub Actions (`ci.yml`) still runs tests, typecheck and build on every push and PR. Rejected: GitHub Pages (the first setup): it works, but a custom domain needs a separate DNS record outside the zone's provider, there are no branch previews, and the project path would need the `/kinetic-ui/` base.

## Known limits
- The step detector is demo-grade. It will misread a phone in a swinging bag, running (over the band), stairs, vehicles (bumpy roads can land in the band), and slow walkers below 1.5 steps/s. The asymmetric hysteresis and the Show-full escape hatch exist because of this.
- Background tabs: browsers stop `devicemotion` when the page is hidden; the UI decays to still after the exit time.
- Only the first moving episode after a Show-full tap is suppressed until the user stops; a user who never stops walking stays in the full form, which is the safe direction.
- "Session" for Show-full suppression is the page lifetime, not `sessionStorage`. A reload re-enables moving mode.
- No real backend or auth; "Create account" only validates.
- Not a full accessibility audit; tested with keyboard and Playwright's accessibility snapshot, not with VoiceOver/TalkBack on devices.
- Conformance fixtures (`packages/spec`) and unit tests cover the motion state machine, cadence estimator, motion store, Show-full policy, form model and email helpers. UI behaviour was verified with scripted Playwright runs, which are not committed as a test suite.
- npm: the unscoped name `kinetic-ui` belongs to an unrelated, abandoned 2021 package; the `@kinetic-ui` scope is unclaimed. The packages here are private workspace packages and are not published.
